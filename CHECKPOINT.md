# Текущая контрольная точка

## Завершённая задача

TASK-005 — минимальный программный каркас и единая команда качества. Задача
выполнена в ветке `task/005-program-scaffold-quality`; интеграцию в `main` нужно
подтвердить по истории Git после завершения ветки.

## Состояние основной ветки

- TASK-001, TASK-002, TASK-003 и TASK-004 слиты отдельными merge-коммитами.
- TASK-005 оформлена одним атомарным содержательным коммитом в собственной ветке.
- Удалённый репозиторий не настроен и не требуется в текущем объёме.

Текущий SHA, активную ветку, факт интеграции и чистоту дерева следует подтверждать
через Git, поскольку документ не дублирует изменяемые идентификаторы истории.

## Что уже существует

- Локальный Git-репозиторий, проектные правила и переносимые документы состояния.
- CPython `>=3.14,<3.15`, `.python-version` для 3.14.7, `uv`, `pyproject.toml`,
  зафиксированный `uv.lock` и устанавливаемый `src`-пакет
  `real_estate_parser`.
- Pydantic 2.x как единственная runtime-зависимость; pytest, Ruff и mypy как
  development-зависимости.
- Переносимая команда `uv run quality`: Ruff format-check, Ruff lint, строгий
  mypy, smoke pytest и отдельный pytest-этап fixture integrity.
- Офлайн-проверки всех manifest-связей, JSON-синтаксиса, UTF-8 без BOM и
  канонических byte-exact `expected/search-*.json`.
- Проект первого локального среза: JSON-фикстура → строгая валидация → фиктивный
  адаптер → нормализация → атомарная коллекция → стандартный поиск →
  детерминированный JSON.
- Предметная идентичность, канонические типы, происхождение каждого значения,
  `Present`/`Missing`/`Unsupported`, стабильные ошибки, поиск и сортировка TASK-003.
- Точные внешние документы `fixture-source-batch@1` и `search-criteria@1`,
  версионированный каталог `tests/fixtures/v1`, негативная матрица и byte-exact
  oracle TASK-004.

## Что намеренно не реализовано

- Предметные Python-типы и Pydantic-модели внешних документов.
- Чтение JSON как граничная операция, `ValidatedSourceBatch`, source adapter,
  нормализация, коллекция, поиск, mapper и сериализатор результата.
- Пользовательский CLI первого среза.
- Несколько наблюдений, постоянное хранилище, история изменений и дедупликация.
- Физический объект недвижимости, база данных, API, HTTP, HTML и реальные
  площадки.
- Нестандартные сигналы, ИИ, уведомления, UI, OpenClaw и Telegram.
- Docker, CI, развёртывание, удалённый репозиторий и динамический загрузчик
  плагинов.

## Рекомендуемая следующая задача

  объекта для дедупликации?
- Какое постоянное хранение потребуется и какие измеренные требования определят
  его выбор?

  реального источника?
- Когда составному нормализованному значению понадобится происхождение из
  нескольких исходных полей?
- Как измерять качество дедупликации и доказательных сигналов?

Ответы не должны приниматься молча: существенные решения оформляются в
`docs/decisions/` в рамках назначенных задач.
