# 0001. Python-базис приложения

- Статус: принято
- Дата: 2026-08-31
- Задача: TASK-002

## Контекст

Проекту нужны частое преобразование неоднородных данных, строгая фиксация происхождения, детерминированные правила, тестируемые адаптеры источников и возможность позднее подключить обработку текста. Первый срез должен быть простым для локального запуска на Windows и Linux, не требовать сервера и не приносить инфраструктуру, которая пока не проверяет архитектуру.

На 2026-08-31 Python 3.14 находится в стабильной фазе bugfix и поддерживается до октября 2030 года. `uv` заявляет полную поддержку CPython 3.14, управляет версией Python, проектом и кроссплатформенным lock-файлом. Эти свойства позволяют зафиксировать одну воспроизводимую среду без набора разрозненных инструментов.

## Критерии выбора

- выразительность для нормализации и проверяемой обработки данных;
- развитая экосистема будущих HTTP-, HTML- и текстовых адаптеров без их немедленного подключения;
- строгая проверка недоверенных данных на границах;
- возможность статически проверять контракты;
- быстрые модульные и сквозные тесты;
- воспроизводимая установка на Windows и Linux;
- небольшой набор инструментов и зависимостей;
- отсутствие привязки ядра к веб-фреймворку, базе данных или ИИ.

## Рассмотренные варианты

### Python

Сильные стороны: лаконичная обработка данных, зрелые библиотеки валидации и тестирования, естественный путь к будущему анализу текста и широкий выбор адаптеров. Риск: динамическая природа языка позволяет размывать границы. Риск компенсируется обязательными аннотациями, строгой статической проверкой, небольшими контрактами и запретом передавать неструктурированные словари через ядро.

### TypeScript на Node.js

Сильные стороны: единый язык с возможным веб-интерфейсом, сильная экосистема сетевых и браузерных инструментов, удобная асинхронность. Недостаток для текущего среза: типы не проверяют данные во время выполнения, поэтому всё равно нужна отдельная схема валидации; связь с будущим интерфейсом пока не даёт выгоды, а предметная обработка остаётся серверной.

### Go

Сильные стороны: простой переносимый бинарный файл, строгая компиляция и эффективная конкурентность. Недостаток для текущего среза: больше служебного кода при быстро меняющейся схеме неоднородных объявлений и менее прямой путь к будущим экспериментам с обработкой текста. Производительность Go пока не отвечает измеренному ограничению проекта.

## Решение

### Среда выполнения и проект

- CPython `3.14.x`.
- В будущем `pyproject.toml` задаёт `requires-python = ">=3.14,<3.15"`.
- `uv` управляет интерпретатором, виртуальной средой, зависимостями, командами и `uv.lock`.
- `uv.lock` коммитится; `.venv/` не коммитится.
- Используется `src`-layout с одним пакетом `real_estate_parser`.
- Создаются только модули, нужные текущей задаче; пустые каталоги будущих подсистем не генерируются.

### Модели и границы

- Pydantic `2.x` используется в строгом режиме для внешних JSON-структур и представления результата; точный выпуск фиксируется будущим `uv.lock`, а переход на следующую основную версию требует отдельной задачи.
- Лишние поля недоверенного входа отклоняются, если контракт явно не разрешает обратное.
- После проверки граничная модель преобразуется в обычные типизированные объекты ядра.
- Pydantic, JSON и CLI не проникают в предметные правила и контракты ядра.
- Точные сущности, единицы измерения и состояния неопределённости определяет TASK-003.

### Проверки качества

- pytest — тестовый раннер, фикстуры и проверки ошибок.
- Ruff — единственный форматтер и линтер; отдельные Black, isort и Flake8 не добавляются.
- mypy со строгим базовым режимом — статическая проверка типов всего `src` и тестируемых контрактов.
- Стандартная библиотека Python используется для JSON, CLI и логирования, пока не доказана необходимость внешней зависимости.

### Что не выбирается сейчас

- база данных, ORM и миграции;
- веб-фреймворк и API;
- HTTP-клиент, HTML-парсер и браузерная автоматизация;
- очередь, планировщик и распределённое выполнение;
- Docker и платформа развёртывания;
- UI, OpenClaw, Telegram и ИИ;
- библиотека геокодирования или пространственная база данных.

Новая зависимость добавляется только задачей, где она нужна проверяемому результату, с объяснением, почему стандартной библиотеки недостаточно.

## Последствия

- Первый кодовый срез сможет запускаться одинаковой короткой командой через `uv`.
- На старте будет одна обязательная runtime-зависимость — Pydantic; инструменты качества относятся к development-группе.
- Границы будут проверяться и во время выполнения, и статически.
- Переход на API или постоянное хранилище не потребует менять предметное ядро, если контракты соблюдены.
- Python может потребовать оптимизации позднее, но решение о ней принимается только по профилированию реальной нагрузки.

## Проверка и условия пересмотра

Решение проверяется первым срезом: чистая установка, успешные тесты, статическая проверка, запуск фикстуры и детерминированный результат на Windows и Linux. Пересмотр нужен, если измерения покажут неприемлемую производительность, ключевой источник окажется несовместим с экосистемой или эксплуатационная среда запретит выбранный runtime.
