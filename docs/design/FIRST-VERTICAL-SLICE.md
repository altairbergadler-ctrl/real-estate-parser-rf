# Первый локальный сквозной срез

## Назначение

Проверить, что модульный монолит может провести недоверенные данные через независимые границы источника, нормализации и стандартного поиска, сохранив происхождение значений. Сценарий не предназначен для полезного поиска реальных объектов и не обращается к сети.

## Внешний сценарий

Будущая команда получает пути к JSON-файлу объявлений и JSON-файлу критериев. Точное имя команды фиксируется при создании каркаса, но интерфейс должен соответствовать форме:

```text
uv run real-estate-parser search --listings <listings.json> --criteria <criteria.json>
```

При успехе стандартный поток содержит только один корректный JSON-документ результата. Диагностические сообщения не смешиваются с данными. Код завершения равен нулю только при полном успешном прохождении входа.

## Входные данные

### Объявления

Фикстура содержит небольшой массив полностью вымышленных записей одного источника. Она должна включать:

- устойчивый идентификатор публикации в источнике;
- исходный URL в вымышленном домене;
- время наблюдения;
- текстовое местоположение;
- цену и валюту в формате источника;
- общую площадь в формате источника;
- число комнат в формате источника;
- дополнительные данные, необходимые для проверки реакции контракта на неизвестное поле.

Точные имена, типы, единицы и представление отсутствующего значения определяет TASK-003. TASK-004 создаёт конкретные фикстуры.

### Критерии

Минимальный стандартный поиск должен уметь выразить верхнюю границу цены, нижнюю границу площади и допустимое число комнат. Все критерии применяются конъюнктивно. Неуказанный критерий не ограничивает результат.

## Поток и границы

```text
CLI adapter
  -> input validation
  -> fixture source adapter
  -> normalization application service
  -> in-memory collection
  -> search application service
  -> output mapping and validation
  -> JSON stdout
```

- Входной адаптер знает файлы, JSON, аргументы и коды завершения.
- Адаптер источника знает только формат фиктивного источника и реализует входной контракт приложения.
- Нормализация не знает CLI и преобразует только явно поддержанные поля.
- Поиск получает нормализованные объекты и типизированные критерии, не зная источник.
- Выходной адаптер превращает результат в граничную модель и JSON.
- Направление зависимостей идёт к предметным типам и прикладным контрактам.

## Минимальное происхождение

Каждое значение, показанное в совпавшем результате, должно позволять определить:

- источник;
- идентификатор публикации;
- исходное поле или фрагмент;
- исходное значение;
- время наблюдения;
- версию правила нормализации.

Структура происхождения задаётся TASK-003. Нельзя выводить нормализованное значение, если связь с исходным значением потеряна.

## Поведение при ошибках

- Невалидный JSON, неверный тип, обязательное отсутствующее поле и запрещённое лишнее поле завершают запуск ошибкой.
- Ошибка содержит стабильную категорию, путь к входной записи и полю, но не трассировку по умолчанию.
- Частичный результат при ошибке входа не выдаётся.
- Неподдерживаемое или отсутствующее значение не подменяется нулём или догадкой.
- Корректный вход без совпадений возвращает успешный пустой список, а не ошибку.

## Детерминизм

Для одинаковых файлов и версии правил байтовое содержимое JSON-результата должно совпадать, кроме полей, которые TASK-003 явно признает внешними метаданными запуска. Порядок совпадений задаётся устойчивым составным ключом, а ключи JSON сериализуются в стабильном порядке.

## Критерии приёмки будущей реализации

- Чистая среда воспроизводится из `pyproject.toml` и `uv.lock`.
- Одна команда запускает форматирование в режиме проверки, линтинг, mypy и pytest.
- Валидная фикстура проходит полный поток и выбирает ожидаемые объявления.
- Результат показывает только нормализованные поля первого среза и происхождение каждого из них.
- Повторный запуск даёт идентичный результат.
- Невалидная фикстура даёт ожидаемую категорию ошибки и ненулевой код без частичного JSON.
- Тесты отдельно доказывают независимость нормализации и поиска от CLI и Pydantic-моделей.

## Не входит в первый срез

- реальные сайты, HTTP и HTML;
- постоянное хранилище и миграции;
- дедупликация;
- сохранённые поиски и уведомления;
- нестандартные и ИИ-сигналы;
- API и пользовательский интерфейс;
- OpenClaw и Telegram;
- Docker, фоновые задачи и распределённая обработка;
- геокодирование и полнотекстовый поиск.

## Последовательность следующих задач

1. TASK-003 — определить предметные типы и контракты, необходимые этому документу.
2. TASK-004 — создать стратегию проверок и спецификацию фикстур.
3. Отдельная задача — создать только исполняемый каркас и проверки качества.
4. Последующие небольшие задачи — по одному добавить входной адаптер, нормализацию, поиск и итоговый сквозной тест.

Ни один из этих пунктов не реализуется автоматически в рамках TASK-002.
